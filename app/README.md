# Часть первая

## Цель изменений

1. Унифицировать представление рецептов во всех слоях приложения – теперь используется единая модель `NetworkRecipe` (domain-слой), не зависящая от конкретных таблиц локальной БД.
2. Упростить локальное хранение: оставлены только таблицы `cashRecipes` (кэш сетевых рецептов) и `savedRecipes` (избранное). Пользовательские рецепты временно вынесены на серверную часть.
3. Повысить стабильность сетевого слоя: замена прямого подключения к Turso (libsql) на HTTP‑запросы к Turso Pipeline API.
4. Добавить поддержку приватности рецептов (`isPublic`), а также списков пользователей, лайкнувших и сохранивших рецепт.

- Ингредиенты (`ingredients`) временно возвращаются пустым списком; предполагается их получение отдельным запросом.
- Сохранён fallback‑режим: при отсутствии интернета используется локальный кэш.

## Структура ответа Turso HTTP API (Pipeline)

При использовании HTTP‑метода `POST` на эндпоинт `https://<your-db>.turso.io/v2/pipeline`  
тело запроса должно содержать JSON вида:

```json
{
  "requests": [
    { 
      "type": "execute", 
      "stmt": { "sql": "SELECT * FROM Recipes" } 
    },
    { "type": "close" }
  ]
}
```

Ответ сервера имеет следующую структуру (успешный ответ, `200 OK`):

```jsonc
{
  "baton": null,            // внутренний идентификатор (можно игнорировать)
  "base_url": null,         // базовый URL (можно игнорировать)
  "results": [              // массив результатов каждого запроса из "requests"
    {
      "type": "ok",         // результат первого запроса ("execute")
      "response": {
        "type": "execute",  // тип результата
        "result": {
          "cols": [         // описание колонок
            { "name": "title", "decltype": "TEXT" },
            { "name": "cookTime", "decltype": "INTEGER" }
            // ... остальные колонки
          ],
          "rows": [         // массив строк с данными
            [               // каждая строка — массив ячеек
              { "type": "text", "value": "Спагетти Карбонара" },
              { "type": "integer", "value": "25" }
              // ... ячейки в порядке колонок
            ],
            [               // следующая строка
              { "type": "text", "value": "Омлет с овощами" },
              { "type": "integer", "value": "10" }
            ]
          ]
        }
      }
    },
    {
      "type": "ok",         // результат второго запроса ("close")
      "response": {
        "type": "close"     // подтверждение закрытия
      }
    }
  ]
}
```

### Пояснения

- **`results`** содержит ровно столько элементов, сколько было отправлено запросов в `"requests"`.
- Каждый элемент `results` имеет поле `type`:
  - `"ok"` – запрос выполнен успешно;
  - `"error"` – произошла ошибка (содержит описание ошибки).
- Для запросов типа `"execute"` внутри `response` находится объект `result` с полями:
  - `cols` – массив определений колонок (`name`, `decltype`).
  - `rows` – массив строк; каждая строка – массив ячеек.  
    Ячейка – объект с полем `type` (тип данных: `"text"`, `"integer"` и др.)  
    и полем `value` в виде строки.
- Запрос `"close"` освобождает ресурсы соединения на сервере; его обязательно нужно отправлять последним.

### Пример кода для разбора (Android/Kotlin)

```kotlin
val okResult = resultsArray.getJSONObject(0)
if (okResult.getString("type") != "ok") { /* обработка ошибки */ }

val resultObj = okResult
    .getJSONObject("response")
    .getJSONObject("result")

val columns = resultObj.getJSONArray("cols")
val rows = resultObj.getJSONArray("rows")

// Карта: имя колонки -> индекс
val colIndex = mutableMapOf<String, Int>()
for (i in 0 until columns.length()) {
    val col = columns.getJSONObject(i)
    colIndex[col.getString("name")] = i
}

// Разбор строки
for (i in 0 until rows.length()) {
    val row = rows.getJSONArray(i)
    val title = row.getJSONObject(colIndex["title"]!!).getString("value")
    // ...
}
```

## Цель изменений

---

## Внесенные изменения

### 1. Глобальные настройки и зависимости
- **BuildScript**: Вынос ключевых переменных (URL базы данных, токены авторизации) в конфигурационные файлы для повышения безопасности и удобства настройки.

### 2. Слой предметной области (Domain)
- **Создана модель `User`**: Единый data-класс для представления данных пользователя во всем приложении.
- **Интерфейс `InternetChecker`**: Введен для абстрагирования проверки сети, что позволило избавить репозитории от прямой зависимости от Android Context.

### 3. Слой данных (Data)
- **`Turso.kt`**:
    - Удалены все зависимости от UI (`Context`, `MainActivity`, `Toast`, `NavController`).
    - Все методы авторизации и регистрации переведены на использование `suspend` функций.
    - Методы возвращают чистые данные или логические результаты, не инициируя навигацию.
- **`UserRemoteRepository`**:
    - Инкапсулирует логику взаимодействия с Turso API для задач пользователя.
    - Внедрена проверка соединения через `InternetChecker` перед каждым запросом.
- **`RecipeRemoteRepository`**: Обновлен для использования `InternetChecker`.
- **`UserQueries`**: Дополнены SQL-запросами для сброса и проверки обновления пароля.
- **`AndroidInternetChecker`**: Реализация интерфейса проверки сети с использованием системного `ConnectivityManager`.

### 4. Слой представления (Presentation)
- **Refactoring ViewModels**:
    - **`LoginViewModel`** и **`RegistrationViewModel`**: Теперь являются единственными владельцами бизнес-логики авторизации.
    - Используют `StateFlow` для управления состоянием операций (`loginResult`, `registrationResult`, `findUserResult`, `resetPasswordResult`).
    - Полностью управляют асинхронными вызовами к репозиториям через `viewModelScope`.
- **DI (Dependency Injection)**:
    - Созданы специализированные фабрики: `LoginViewModelFactory` и `RegistrationViewModelFactory`.
    - Инициализация всех зависимостей (Turso, Repositories, ViewModels) централизована в `MainActivity`.
- **UI-фрагменты**:
    - `LoginFragment`, `RegistrationFragment`, `VerifyOTP`, `ForgetPassword`, `SetNewPassword` теперь только подписываются на изменения состояния во ViewModel.
    - Логика навигации, показа ошибок (Toast) и управления сессиями (`SessionManager`) перенесена из сетевого слоя непосредственно во фрагменты.

### 5. Исправление ошибок и стабильность
- Оптимизирована работа с `SessionManager`: сессии создаются только после подтверждения успешных операций от сервера.

## Итог

В результате рефакторинга достигнуто четкое разделение ответственности:
- **UI** только отображает данные и реагирует на действия пользователя.
- **ViewModel** управляет состоянием и бизнес-логикой.
- **Repository** отвечает за источник данных и проверку условий (интернет).
- **Remote API (`Turso`)** занимается исключительно сетевым взаимодействием.

# Часть пятая (интеграция камеры и сервиса ImgBB)

1. Реализация функционала смены аватара пользователя.
2. Интеграция с системной камерой и галереей для выбора изображений.
3. Использование облачного сервиса ImgBB для хранения фотографий профиля.
4. Синхронизация ссылок на изображения с серверной БД Turso.

---

## Внесенные изменения

### 1. Работа с изображениями
- **ImgBB API**: Создан Retrofit-клиент (`ImgBBService`) для загрузки изображений в формате Base64. Ключ API вынесен в `BuildConfig.IMGBB_KEY`.
- **Выбор фото**: В `ProfileFragment` реализован диалог выбора источника (Камера/Галерея) с использованием современного **ActivityResult API**.
- **Обработка**: Реализована конвертация `Bitmap` и `Uri` в Base64 с предварительным сжатием для оптимизации сетевого трафика.
- **Отображение**: Интегрирована библиотека **Glide** для асинхронной загрузки, кеширования и плавного отображения аватаров из сети.

### 2. Слой данных и домен
- **`User` модель**: Добавлено поле `avatarUrl`.
- **`Turso.kt`**: Добавлен метод `updateAvatar` для сохранения прямой ссылки на изображение в таблице `users`.
- **`UserRemoteRepository`**: Инкапсулирует логику последовательного вызова ImgBB (загрузка файла) и Turso (сохранение ссылки).

### 3. Слой представления (UI)
- **`ProfileViewModel`**: Добавлен метод `uploadAndSetAvatar`, управляющий процессом обновления фото и отслеживающий статус загрузки.
- **`ProfileFragment`**: Реализованы обработчики разрешений (Runtime Permissions) для камеры и логика обновления UI при успешной смене фото.
- **Glide Integration**: Аватар теперь загружается автоматически при открытии профиля любого пользователя.

### 4. Конфигурация
- **`AndroidManifest.xml`**: Добавлены разрешения `CAMERA` и описание соответствующей feature.
- **`MainActivity`**: Добавлена инициализация `ImgBBService` и передача его в репозиторий.


## Итог

В приложение добавлен полноценный функционал персонализации профиля. Использование ImgBB позволило разгрузить серверную БД от хранения бинарных данных, сохранив при этом высокую скорость работы за счет облачного хранилища и библиотеки Glide.
